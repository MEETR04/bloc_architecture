# Flutter API & Data Layer Guidelines

Apply these rules every time you add or modify API calls, repositories, use cases, models, or DI registration in this project.

---

## Layer Architecture

Every feature follows a strict 4-layer split. Never collapse layers.

```
feature/
  data/
    datasource/   ← Retrofit @RestApi interface + generated .g.dart
    repository/   ← Concrete implementation of the domain interface
  domain/
    repository/   ← Abstract interface (IXxxRepository)
    usecases/     ← One class per business action
  models/
    request/      ← Request body DTOs (json_serializable)
    response/     ← Response DTOs (json_serializable)
  bloc/           ← Presentation state machine
```

---

## Datasource — Retrofit API

- Use `@RestApi` abstract class generated by `retrofit`. Never hand-write `dio.get(...)` calls directly in a repository.
- File must end in `_api.dart` and include `part '<name>_api.g.dart';`.
- All endpoints are constants in `APIEndPoints` — never inline URL strings.
- Return typed response models directly; do not return `Response<dynamic>`.

```dart
@RestApi(baseUrl: APIEndPoints.baseUrl)
abstract class UserApi {
  factory UserApi(Dio dio, {String baseUrl}) = _UserApi;

  /// Fetches paginated user list from the server.
  @GET(APIEndPoints.getUsers)
  Future<UserListResponse> getUsers(@Query('page') int page);
}
```

- After modifying a `_api.dart`, always run:
  ```
  dart run build_runner build
  ```

## Repository Interface (Domain)

- Prefix with `I` → `IXxxRepository` in `domain/repository/`.
- Use `abstract interface class`, not `abstract class`.
- Method signatures match use-case needs exactly — no extra parameters.
- Return raw response models (not `AppResult`); use cases own the result wrapping.

```dart
abstract interface class IUserRepository {
  Future<UserListResponse> getUsers(int page);
}
```

---

## Repository Implementation (Data)

- Implement the domain interface: `class UserRepository implements IUserRepository`.
- Inject the datasource through the constructor (no `locator` calls inside the class).
- Every method wraps the datasource call in `try/catch`:
  - `DioException` → extract message from `e.response?.data` if available, then throw `AppException`.
  - Generic `catch (e)` → throw `AppException(e.toString())`.
- Never swallow exceptions silently.

```dart
class UserRepository implements IUserRepository {
  const UserRepository(this._api);
  final UserApi _api;

  @override
  Future<UserListResponse> getUsers(int page) async {
    try {
      return await _api.getUsers(page);
    } on DioException catch (e) {
      final msg = e.response?.data is Map
          ? e.response?.data['error']?.toString()
          : null;
      throw AppException(msg ?? e.message ?? e.error.toString());
    } catch (e) {
      throw AppException(e.toString());
    }
  }
}
```

## Use Cases

- One class per action, named `<Action>UseCase`.
- Single public method: `call(...)` (makes it callable).
- Return `AppResult<T>` — never throw from a use case; catch and return `Failure(...)`.
- Perform all input validation before the repository call; return `Failure` for invalid input.
- Inject the domain interface (not the concrete repository).

```dart
class GetUsersUseCase {
  const GetUsersUseCase(this._repository);
  final IUserRepository _repository;

  Future<AppResult<UserListResponse>> call(int page) async {
    if (page < 1) return const Failure('Page must be >= 1');
    try {
      final result = await _repository.getUsers(page);
      return Success(result);
    } catch (e) {
      return Failure(e.toString());
    }
  }
}
```

## Models — Request / Response

- Use `json_serializable` + `freezed` (or just `json_serializable`) — no manual `fromJson`/`toJson`.
- Request models → `models/request/<name>_request_model.dart`
- Response models → `models/response/<name>_response_model.dart`
- All fields nullable by default unless the API guarantees presence.
- Use `@JsonKey(name: 'snake_case')` when the JSON key differs from the Dart field name.

```dart
@JsonSerializable()
class LoginRequestModel {
  const LoginRequestModel({required this.email, required this.password});

  final String email;
  final String password;

  factory LoginRequestModel.fromJson(Map<String, dynamic> json) =>
      _$LoginRequestModelFromJson(json);
  Map<String, dynamic> toJson() => _$LoginRequestModelToJson(this);
}
```

After modifying a model, regenerate:
```
dart run build_runner build
```

## Endpoints

- All base URLs and path constants live in `APIEndPoints` (`core/api/api_endpoints.dart`).
- Never duplicate or inline endpoint strings anywhere else.
- Group paths by feature with a comment block.

```dart
class APIEndPoints {
  // Auth
  static const login = '/login';
  static const register = '/register';
  // Users
  static const getUsers = '/users';
}
```

## Exception Hierarchy

Use the existing typed exceptions from `core/api/exceptions/app_exception.dart`:

| Exception | When |
|---|---|
| `AppException` | Generic fallback |
| `UnauthorisedException` | HTTP 401 |
| `BadRequestException` | HTTP 402–417 |
| `ServerSideException` | HTTP 500–505 / timeouts |
| `ConnectionException` | Socket / network drop |
| `NoInternetException` | No connectivity |
| `RequestCanceledException` | Request cancelled / timeout |

- Never throw raw `DioException` up through the repository boundary.
- `DioExceptionUtil.handleError` is available for centralised Dio error mapping.

## Dependency Injection (GetIt)

- All registration happens in `locator.dart`; never call `locator.registerX` elsewhere.
- Registration order: network → datasource → data repository → use cases → BLoC.
- Datasources and `Dio` → `registerSingleton` (shared, stateless).
- Repositories and use cases → `registerLazySingleton` (created on first use).
- BLoCs → `registerFactory` (new instance per screen).
- Register against the **interface**, not the concrete class:
  ```dart
  locator.registerLazySingleton<IUserRepository>(
    () => UserRepository(locator<UserApi>()),
  );
  ```

---

## Bloc Integration

- BLoC receives use cases via constructor — never call `locator` inside a BLoC.
- Use `AppResult` pattern-matching with exhaustive `switch` to emit states:

```dart
final result = await _getUsersUseCase(page);
switch (result) {
  case Success(:final data):
    emit(HomeLoaded(users: data.data ?? []));
  case Failure(:final message):
    emit(HomeError(message: message));
}
```

- Emit a loading state before every async operation.
- Never `await` inside `emit`; emit immediately, then await.

---

## Logging

- `debugPrint` only — never `print`.
- Log before and after API calls at the repository level when debugging.
- HTTP logging is handled globally by `HttpLoggerInterceptor` in debug mode — do not duplicate it.

---

## Parallelisation

- Use `Future.wait([...])` when multiple independent calls are needed in the same use case.
- Never fire sequential awaits for calls that have no dependency on each other.

```dart
// ✅ Parallel
final (users, profile) = await (
  _userRepo.getUsers(1),
  _profileRepo.getProfile(),
).wait;

// ❌ Sequential — wasteful
final users = await _userRepo.getUsers(1);
final profile = await _profileRepo.getProfile();
```

## Checklist for a New Feature's API

- [ ] Add endpoint constant to `APIEndPoints`
- [ ] Create `_api.dart` with Retrofit interface
- [ ] Run `build_runner` to generate `.g.dart`
- [ ] Create request/response models with `json_serializable`
- [ ] Run `build_runner` again for models
- [ ] Create `IXxxRepository` interface in domain
- [ ] Create `XxxRepository` implementation in data
- [ ] Create use case(s) in domain/usecases
- [ ] Register everything in `locator.dart` in correct order
- [ ] Inject use case into BLoC; update BLoC states/events
